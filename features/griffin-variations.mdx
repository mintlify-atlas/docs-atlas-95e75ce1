Griffin is Brave's implementation of Chromium's Finch variations service — a backend that lets Brave progressively enable features, run private statistical experiments, and push configuration parameter changes to browsers in the field. Every study definition is open source, seed fetches are served through a CDN that never persists logs, and experiment reporting is restricted exclusively to P3A (Privacy-Preserving Product Analytics). Users who disable P3A opt out of all experiment reporting.

## Three Core Capabilities

Griffin provides three distinct services to engineering and product teams.

<CardGroup cols={3}>
  <Card title="Staged Rollouts" icon="chart-line">
    Gradually enable a feature flag for an increasing percentage of the user population, catching regressions before they reach everyone.
  </Card>
  <Card title="Private Statistical Experiments" icon="flask">
    Randomly assign browsers into groups and compare outcomes through P3A metrics — without identifying individual users.
  </Card>
  <Card title="Parameter Updates" icon="sliders">
    Change remote configuration values (timeouts, thresholds, URLs) without shipping a hotfix build.
  </Card>
</CardGroup>

## Privacy Guarantees

Brave's privacy commitments place hard limits on how Griffin can be used.

<Accordion title="Unchanged Data Collection Policy">
Griffin touches the data-collection surface in exactly two ways. First, the browser periodically fetches a seed file from Brave's CDN — those request logs are never persisted. Second, statistical experiments can feed results back through P3A. No other telemetry mechanism is permitted; if P3A is disabled by the user, experiment reporting stops entirely.
</Accordion>

<Accordion title="Open Source and Auditable">
Every part of the system is publicly inspectable:

- Chromium's variations service component: [`components/variations/service/variations_service.h`](https://source.chromium.org/chromium/chromium/src/+/master:components/variations/service/variations_service.h)
- Seed generation, signing, and serving: [`brave/brave-variations`](https://github.com/brave/brave-variations) repository
- All feature implementations: search for `base::Feature` in [`brave/brave-core`](https://github.com/brave/brave-core)

To inspect which studies are active in your browser, navigate to `brave://version` or visit [griffin.brave.com](https://griffin.brave.com/).
</Accordion>

<Accordion title="Privacy Reviews">
Every proposed study goes through a privacy review before it can run. Reviews verify that experiment groups are large enough to prevent individual user identification, and that page-visible UI changes do not increase the JavaScript fingerprinting surface exposed to websites.
</Accordion>

## How Seeds Work: Studies → Experiments → Features

The variations service uses a **seed file** — a signed configuration document hosted on Brave's CDN — that organises variations into a three-level hierarchy.

```
Seed file
└── Study  (filter rules: country, platform, version)
    └── Experiment  (group, e.g. "Group A" / "Group B")
        └── Feature  (base::Feature + optional key/value parameters)
```

<Steps>
  <Step title="Study">
    A named set of experiments with filter rules that restrict which clients are eligible (by country, platform, and Brave version). In an A/B test each eligible browser independently selects a group by evaluating a biased coin flip derived from Chromium's [field trials](https://source.chromium.org/chromium/chromium/src/+/master:base/metrics/field_trial.h).
  </Step>
  <Step title="Experiment">
    A "group" that enables and/or disables a set of `base::Feature` flags, each carrying optional key/value parameters. The sign-up probability across all experiments in a study sums to ≤ 1.0; the remainder falls into the default (no-experiment) bucket.
  </Step>
  <Step title="Feature">
    Chromium's standard [feature toggle](https://en.wikipedia.org/wiki/Feature_toggle) abstraction. In brave-core, features are declared with `BASE_DECLARE_FEATURE` and searched at runtime using `base::FeatureList::IsEnabled()`.

    ```cpp
    // Example feature flag checked at runtime
    if (base::FeatureList::IsEnabled(features::kMyNewFeature)) {
      // Feature-enabled code path
    }
    ```
  </Step>
</Steps>

## Platform Behavior

First-launch and restart requirements differ across platforms.

| Platform | First-Launch Studies | Restart Required |
|---|---|---|
| **Windows (stub/online installer)** | ✅ Applied on first launch | No |
| **Windows (standalone/offline installer)** | Seed fetched but not applied | **Yes** |
| **macOS** | Seed fetched but not applied | **Yes** |
| **Linux** | Seed fetched but not applied | **Yes** |
| **Android** | ✅ Applied on first launch | No |
| **iOS (v1.63+)** | Seed fetched but not applied | **Yes** |

<Note>
Any seed update downloaded while the browser is running — regardless of platform — only takes effect after the next browser restart.
</Note>

## Seed Fetch Schedule

<Tabs>
  <Tab title="Desktop (Windows / macOS / Linux)">
    - **At startup:** an immediate fetch fires.
    - **Repeating:** every **30 minutes** thereafter.
    - **On failure:** the next attempt is scheduled **5 minutes** after a failed fetch.
  </Tab>
  <Tab title="Mobile (Android / iOS)">
    There is no repeating timer. Instead:

    - **At startup:** fetches only when `now > last_fetch_time + 30 min` (throttled via a stored preference). On Android fresh installs this first fetch can briefly block startup so that studies apply on the very first launch.
    - **On foreground:** waits 5 seconds, then applies the same 30-minute throttle check.
  </Tab>
</Tabs>

## Best Practices Workflow

Follow this lifecycle to ship a feature safely via Griffin.

<Steps>
  <Step title="Create the feature flag off by default">
    Declare a `base::Feature` with `FEATURE_DISABLED_BY_DEFAULT`. Optionally expose it in `brave://flags` for local development.

    ```cpp
    BASE_FEATURE(kMyNewFeature,
                 "MyNewFeature",
                 base::FEATURE_DISABLED_BY_DEFAULT);
    ```
  </Step>
  <Step title="Enable on Nightly / Beta via Griffin">
    Open a PR in the `brave-variations` repository and test it locally before merging:

    Launch Brave with the `--variations-pr=1234` flag (replace `1234` with your PR number) to load the seed from that pull request locally.

    Always land on Nightly first, then Beta.
  </Step>
  <Step title="Gradual rollout to Release">
    As train migrations happen, enable the feature on the Release channel through a Griffin study with a gradual rollout percentage, or enable it by default in code — or both.
  </Step>
  <Step title="Enable by default in master before Release ships">
    Set `base::FEATURE_ENABLED_BY_DEFAULT` in master **before** the Griffin study enables the feature for Release users. This ensures CI (unit tests, browser tests, ASAN/MSAN builds) exercises the enabled code path before real users see it.

    ```cpp
    // Switch to enabled-by-default once the feature is proven stable
    BASE_FEATURE(kMyNewFeature,
                 "MyNewFeature",
                 base::FEATURE_ENABLED_BY_DEFAULT);  // ← changed
    ```
  </Step>
  <Step title="Set max_version and retire the study">
    Once the Release channel has the feature on by default in code, set a `max_version` filter in the Griffin study rather than deleting the experiment outright. This prevents older browsers that haven't received the code change from being affected.
  </Step>
  <Step title="Remove the feature flag from the codebase">
    Delete the `base::Feature` declaration and all `IsEnabled()` call sites. The flag is no longer needed.
  </Step>
</Steps>

<Warning>
Never enable a feature on the Release channel via Griffin without first enabling it by default in code on `master`. Skipping this step means CI never exercises the enabled path before it reaches release users.
</Warning>

## Inspecting Active Studies

Navigate to `brave://version` in any Brave browser to see the list of currently active variations. The public dashboard at [griffin.brave.com](https://griffin.brave.com/) shows all live studies across channels.
