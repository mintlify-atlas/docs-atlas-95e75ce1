Brave Wallet is a fully self-custodial, non-custodial cryptocurrency wallet built directly into the browser — no extension required. It supports multiple blockchain networks and their respective cryptographic signature schemes, manages BIP-39 mnemonic key derivation, stores an encrypted keyring locally, and exposes standardized provider APIs (EIP-1193, Solana's wallet standard, and equivalents for Bitcoin, Filecoin, Zcash, and Cardano) to web dApps. The wallet is structured as an iOS-compatible layered component that keeps all sensitive cryptographic operations in a sandboxed `core/` layer never linked against the Content API.

## Supported Chains and Cryptography

Each supported network uses a distinct signature algorithm. Brave Core implements all of them natively.

<CardGroup cols={2}>
  <Card title="Ethereum / Bitcoin / Filecoin / Zcash (public)" icon="link">
    **ECDSA with secp256k1** — Signing transactions for ETH, BTC, FIL, and public ZCash transactions. Uses the Koblitz curve (not required by TLS), so this is wallet-specific work on top of Chromium's existing ECDSA infrastructure.
  </Card>
  <Card title="Solana / Cardano" icon="circle-nodes">
    **EdDSA with Ed25519 (RFC 8032)** — Signing transactions for SOL and ADA. The Ed25519 implementation is shared with Chromium's standard library; Brave uses it for a different message domain.
  </Card>
  <Card title="Filecoin (imported BLS accounts)" icon="key">
    **BLS12-381** — Used only when a user imports a Filecoin account that requires BLS signing. BLS12-381 keys are not generated by the wallet by default; they must be explicitly imported.
  </Card>
  <Card title="Zcash Orchard (shielded)" icon="shield">
    **RedPallas + zkSNARKs** — The Zcash shielded protocol follows [ZIP-0224 (Orchard)](https://zips.z.cash/zip-0224), which uses the RedPallas signature scheme and zero-knowledge proof system. Desktop support is available; iOS support is planned.
  </Card>
  <Card title="Polkadot (upcoming)" icon="clock">
    **Sr25519** — Schnorr signatures over the Ristretto255 curve (Ed25519 under the hood). Not yet released; incoming for Polkadot support.
  </Card>
  <Card title="Key derivation" icon="lock">
    **PBKDF2 (RFC 2898)** — The user's wallet password is stretched using PBKDF2 to derive an AES encryption key that protects the keyring on disk. All platforms use the same derivation.
  </Card>
</CardGroup>

## BIP-39 Mnemonic Key Derivation

Wallet creation starts with a BIP-39 mnemonic. The wallet generates a 12-word mnemonic by default (16 bytes of entropy), or 24 words (32 bytes of entropy) for the legacy Ethereum path.

```cpp
// components/brave_wallet/browser/bip39.h
namespace brave_wallet::bip39 {

inline constexpr uint32_t kSeedSize              = 64;
inline constexpr uint32_t k12WordsEntropySize    = 16;
inline constexpr uint32_t k24WordsEntropySize    = 32;
inline constexpr uint32_t kDefaultEntropySize    = k12WordsEntropySize;
inline constexpr uint32_t kLegacyEthEntropySize  = 32;

// Generate mnemonic from entropy bytes following BIP39.
// Returns std::nullopt on invalid entropy size or allocation failure.
std::optional<std::string> GenerateMnemonic(base::span<const uint8_t> entropy);

} // namespace brave_wallet::bip39
```

The mnemonic is expanded into a 64-byte seed (PBKDF2-HMAC-SHA512 with 2048 iterations as specified by BIP-39), then used to derive chain-specific HD key trees following BIP-44 derivation paths.

## Provider Errors and EIP Compliance

The wallet exposes per-chain provider interfaces over Mojo. Error codes align precisely with the relevant Ethereum Improvement Proposals so web dApps receive the correct rejections:

```cpp
// components/brave_wallet/common/brave_wallet.mojom (excerpt)

// EIP-1193 provider errors
enum ProviderError {
  kSuccess               =     0,
  kUserRejectedRequest   =  4001,  // User rejected the request
  kUnauthorized          =  4100,  // Account/method not authorized
  kUnsupportedMethod     =  4200,  // Method not supported
  kDisconnected          =  4900,  // Provider disconnected
  kChainDisconnected     =  4901,  // Disconnected from specified chain
  kUnknownChain          =  4902,  // Unknown chain
  kInternalError         = -32603,
};

// Solana-specific errors (aligns with solana-client RPC codes)
enum SolanaProviderError {
  kSuccess                             =  0,
  kSendTransactionPreflightFailure     = -32002,
  kTransactionSignatureVerificationFailure = -32003,
  kNodeUnhealthy                       = -32005,
};
```

## Transaction Management

The `tx_service.cc` / `tx_manager.cc` subsystem inside `components/brave_wallet/browser/` handles the full transaction lifecycle: construction, signing, broadcast, and state tracking. Each chain has a dedicated subpath:

| Chain | Path | Key files |
|---|---|---|
| Bitcoin | `browser/bitcoin/` | `bitcoin_base_keyring.cc`, `bitcoin_block_tracker.cc` |
| Zcash | `browser/zcash/` | `v5_zcash_serializer.cc`, `v6_zcash_serializer.cc` |
| General | `browser/` | `tx_service.cc`, `tx_manager.cc`, `tx_state_manager.cc` |

Transaction state is persisted locally via `TxStorage` and can be queried by UI through the Mojo `TxService` interface. Signing always happens inside the sandboxed `core/` layer before a signed transaction bytes are handed back to the browser process for broadcast.

## Wallet Service Architecture

`BraveWalletService` is the central Mojo service entry point for all wallet operations, living in the browser process and communicating with the sandboxed keyring service via dedicated Mojo interfaces.

<Steps>

### Keyring (sandboxed core layer)

The keyring runs in an isolated process. It holds the decrypted private keys in memory only while unlocked and exposes signing-only Mojo methods to the browser process. PBKDF2 key derivation and AES encryption of the keyring are performed here.

### Asset discovery

`AssetDiscoveryManager` and `AssetDiscoveryTask` in `browser/` scan configured chains for on-chain token balances. Discovery results are merged into the local asset registry without sending wallet addresses to any third-party analytics service.

### JSON-RPC clients

Each chain has a dedicated JSON-RPC or REST client (e.g., `EthJsonRpcController`, Bitcoin's `bitcoin_block_tracker.cc`) that routes through Brave's network stack. Requests to public RPC nodes are made through Brave's own infrastructure where possible to reduce third-party fingerprinting.

### dApp provider bridge

The renderer-side provider (`components/brave_wallet/renderer/`) injects `window.ethereum`, `window.solana`, and equivalent objects into web pages. These call back to the browser process via Mojo, which requests user approval through the wallet UI before signing.

</Steps>

## Component Structure

The wallet follows the Chromium [layered-components](https://sites.google.com/a/chromium.org/dev/developers/design-documents/layered-components-design) pattern, enabling an iOS build that reuses `common/` and most of `browser/` without linking against `//content`:

```
components/brave_wallet/
├── api/                    # IDL/WebIDL definitions (asset_ratio.idl)
├── browser/                # Browser-process logic
│   ├── bitcoin/            # Bitcoin-specific keyring and block tracking
│   ├── zcash/              # Zcash serializers (v5 Sapling, v6 Orchard)
│   ├── bip39.cc/h          # BIP-39 mnemonic generation & seed derivation
│   ├── tx_service.cc       # Transaction lifecycle service
│   ├── wallet_handler.cc   # High-level wallet operations
│   └── asset_discovery_manager.cc
├── common/                 # Mojo interfaces + shared types (iOS-safe)
│   ├── brave_wallet.mojom  # All public Mojo contracts
│   ├── brave_wallet_types.h
│   └── buildflags/
├── ios/                    # iOS-only bridge layer
├── renderer/               # Content-layer dApp provider injection
└── resources/              # Icons, token lists, chain metadata
```

<Note>
  The `common/` and `browser/` subtrees deliberately avoid any `//content` API
  dependency so they can be compiled into the iOS target, where only the UIKit
  layer (not Chromium's content layer) is available.
</Note>
