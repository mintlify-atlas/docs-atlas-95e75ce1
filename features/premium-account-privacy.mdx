When you subscribe to a Brave premium service — VPN, Leo AI, or Search Premium — the browser needs to prove you have an active subscription each time you use that service. A naïve approach would be to attach your account ID or email to each request, but that would let the service correlate every request to your payment identity. Brave instead uses a **blind token protocol based on Privacy Pass (RFC 9576)** that mathematically decouples who paid from who is using the service.

The core idea: a server signs tokens it cannot see. Later, when you present a signed token to access a service, the signer cannot recognise it as one they signed because they never saw the original value. This property is called **unlinkability**.

## Protocol Overview

The protocol involves four distinct parties:

<CardGroup cols={2}>
  <Card title="Payment Provider" icon="credit-card">
    Stripe, Apple, or Google. Knows your payment identity and that you purchased a Brave subscription. Knows nothing about which services you use.
  </Card>
  <Card title="Subscription Service" icon="server">
    `payment.bsg.brave.com`. Manages your account and order. Sees that blinded tokens were requested, but never the original token values — cannot link signing requests to later redemptions.
  </Card>
  <Card title="Challenge Bypass Server (CBR)" icon="key">
    The blind signer. Signs blinded tokens and verifies redemptions. Cannot link a signing event to a redemption due to the blinding step.
  </Card>
  <Card title="Premium Service" icon="shield-check">
    Leo, VPN, Search Premium. Knows that a valid credential was presented. Contains no account ID, email, or payment information.
  </Card>
</CardGroup>

## Credential Lifecycle

The full flow, from purchase to service access, proceeds in fourteen steps as illustrated in the source documentation:

```
Payment Provider              Subscription Service            Challenge Bypass Server (CBR)
(Stripe, Apple, Google)       (payment.bsg.brave.com)         (blind signer)
        |                              |                              |
        |  1. User pays                |                              |
        |----------------------------->|                              |
        |                              |  2. Order marked "paid"      |
        |                              |                              |
Browser  --3. Generate random tokens-->|                              |
         --4. Blind tokens locally     |                              |
         --5. Send blinded tokens----->|--6. Forward blinded tokens-->|
                                       |<--7. Signed tokens + proof---|
Browser <--8. Return signed tokens-----|                              |
         --9. Verify DLEQ proof        |                              |
         --10. Unblind tokens locally  |                              |
                                       |                              |
                                Premium Service (Leo, VPN, etc.)
                                       |
Browser --11. Present unblinded token->|
                                       |--12. Verify via CBR--------->|
                                       |<--13. Valid (or 409 reused)--|
                                       |--14. Grant access----------->Browser
```

### Step 1–2: Purchase

The user completes a purchase through a payment provider (Stripe, Apple IAP, or Google Play). The subscription service marks the order as `paid`. No tokens are generated yet, and no credential data is shared with the payment provider.

### Step 3–4: Token Generation (Client-Side)

After a successful purchase, the browser generates fresh random tokens locally using a cryptographic random number generator, then blinds each one before it ever leaves the device. The implementation lives in the Rust SKUs SDK:

```rust
// components/skus/browser/rs/lib/src/sdk/credentials/fetch.rs
let creds: Vec<Token> =
    iter::repeat_with(|| Token::random::<Sha512, _>(&mut csprng))
        .take(num_creds)
        .collect();
let blinded_creds: Vec<BlindedToken> =
    creds.iter().map(|t| t.blind()).collect();
```

Only the `blinded_creds` vector is ever transmitted. The original `creds` remain exclusively on the device.

### Step 5–8: Blind Signing (Server-Side)

The browser sends the blinded tokens to the subscription service, which forwards them to the **Challenge Bypass Server (CBR)**. The CBR signs each blinded token with its issuer key and returns two artifacts:

- **Signed tokens** — blind signatures over the blinded input tokens.
- **Batch proof** — a DLEQ (Discrete Log Equality) proof asserting that the same key was used for every signature in the batch.

### Step 9–10: DLEQ Verification and Unblinding (Client-Side)

Before storing anything, the browser verifies the batch proof. If the proof is invalid, the tokens are discarded with `InternalError::InvalidProof`. Otherwise, the browser removes the blinding factor to recover signed credentials that are valid for presentation:

```rust
// components/skus/browser/rs/lib/src/sdk/credentials/fetch.rs
let unblinded_creds = batch_proof
    .verify_and_unblind::<Sha512, _>(
        &bucket_creds,         // original tokens (never sent to server)
        &bucket_blinded_creds, // blinded versions that were sent
        &signed_creds,         // server's blind signatures
        &public_key,           // issuer's public key
    )
    .or(Err(InternalError::InvalidProof))?;
```

After unblinding, the browser holds credentials that are cryptographically valid but that the CBR cannot recognise as tokens it signed, because it only ever saw the blinded forms.

### Step 11: Credential Presentation (Client-Side)

When accessing a premium service, the browser selects an unspent credential, derives a verification key from it, and signs the issuer identifier (e.g. `brave.com?sku=leo-monthly`) to bind the token to the specific service. This prevents a credential issued for one product from being replayed against a different product:

```rust
// components/skus/browser/rs/lib/src/sdk/credentials/present.rs
let verification_key =
    cred.unblinded_cred.derive_verification_key::<Sha512>();
let signature =
    verification_key.sign::<HmacSha512>(issuer.as_bytes()).encode_base64();
```

The credential is sent as an HTTP cookie containing only:
- Token preimage
- HMAC signature
- Validity window

No account ID, email address, or payment information is included.

### Step 12–14: Redemption (Server-Side)

The premium service forwards the presentation to the CBR, which verifies the signature against its issuer key and checks whether the token preimage has been spent before:

- **New token** — access is granted.
- **Exact replay** (same token, issuer, and binding payload as a prior accepted request) — treated as idempotent and acknowledged without error.
- **True duplicate** (same token, same issuer, different binding payload) — rejected with `409 Conflict`.

Spent-token records are retained until the issuer's expiration window passes, after which they may be purged.

## Credential Types

| Type | Description |
|---|---|
| **TimeLimitedV2** | Primary production type. Tokens are bucketed into time windows (e.g. daily) with per-window sub-issuer keys. Single-use per window, enforced server-side by the CBR. The client also tracks a local `spent` flag per token to avoid unnecessary re-presentation attempts. |
| **SingleUse** | One-time tokens using the same blind signature scheme. Each token can be redeemed exactly once against a given issuer. |
| **TimeLimited (v1)** | Legacy type. Server-generated HMAC-derived tokens — weaker privacy because the server produces the token values directly, enabling it to correlate issuance with redemption. |

`TimeLimitedV2` credentials store `valid_from`, `valid_to`, and a `spent` flag per token in local storage, allowing the SDK to automatically select the correct credential for the current time period.

## Privacy Properties

| Property | How It Is Achieved |
|---|---|
| **Unlinkability** | Blind signing means the CBR signs tokens it cannot see. It cannot later match a presented token preimage to a signing-time blinded token. |
| **No identity in presentation** | The credential cookie contains only the token, its HMAC, and the validity window. No account ID, email, or payment info is transmitted to the premium service. |
| **Double-spend prevention** | The CBR records redeemed token preimages keyed per-issuer and rejects true duplicates (same token, different binding) with `409 Conflict`. Exact replays of a prior accepted redemption are acknowledged idempotently. |
| **Issuer binding** | The HMAC signature binds each token to a specific merchant and SKU, preventing cross-service use of credentials. |
| **Time-limited validity** | TimeLimitedV2 issuers create sub-issuer keys per time window; expired credentials are cryptographically unverifiable. |

## What Each Party Knows

| Party | Knows | Does Not Know |
|---|---|---|
| **Payment provider** (Stripe, Apple, Google) | Your payment identity; that you purchased a Brave subscription | Which credentials you use or when you use premium services |
| **Subscription service** (`payment.bsg.brave.com`) | Your account, order, and that blinded tokens were requested | Original token values; cannot link signing requests to presented credentials |
| **Premium service** (Leo, VPN, Search, etc.) | That a valid credential was presented | Who presented it — no account or payment info is included in the presentation |
| **CBR** (blind signer) | That it signed some blinded tokens; that some tokens were redeemed | Cannot link signing to redemption due to the blinding step |
