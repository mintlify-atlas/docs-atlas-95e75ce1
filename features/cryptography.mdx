Every Chromium-based browser inherits standard TLS 1.3, certificate verification, and HKDF-based session-key derivation from the underlying network stack. Brave adds a second layer of applied cryptography to protect users' identities when they interact with Brave's own services. This page documents each distinct cryptographic feature, the specific algorithm or protocol it uses, which platforms it applies to, and why it was chosen.

<Note>
All cryptographic code described here is open source and lives in the `brave-core` repository. The table entries below map directly to the source documentation at `/docs/cryptography.md`.
</Note>

## Feature Reference Table

| Feature | Cryptography | Platform | Purpose |
|---|---|---|---|
| **Brave Accounts** | RFC 9807 (OPAQUE) | All | Password-authenticated key establishment that keeps the server from learning the user's password |
| **Brave Premium** | Privacy Pass — RFC 9576 (PrivacyPass) | All | Blind token credential system to validate subscriptions without linking payment to usage |
| **Brave Rewards** | VOPRF — RFC 9497 | All | Anonymous rewards and unlinkable access to premium services |
| **Brave Leo (AI)** | HPKE + Oblivious HTTP — RFC 9458 | All | Encrypted relay channel so the inference backend never sees the user's IP |
| **Brave Wallet (ETH/BTC/FIL/ZEC public)** | ECDSA w/ Secp256k1 | All | Signing transactions; same curve as Chromium TLS but applied to blockchain messages |
| **Brave Wallet (SOL/ADA)** | EdDSA w/ Ed25519 — RFC 8032 | All | Signing transactions for Solana and Cardano |
| **Brave Wallet (DOT — unreleased)** | Sr25519 (Schnorr/Ristretto255) | Not released | Polkadot signing; Ed25519 under the hood with Ristretto cofactor clearing |
| **Brave Wallet (Filecoin import)** | BLS12-381 | All | BLS signature scheme for imported Filecoin accounts; not generated by default |

| **Brave P3A** | PPOPRF + Shamir Secret Sharing (STAR) | All | Privacy-preserving telemetry with K-anonymity guarantees |

## Feature Deep Dives

### Brave Accounts — RFC 9807 (OPAQUE)

Brave Accounts use OPAQUE, an asymmetric password-authenticated key exchange (aPAKE) protocol standardised as RFC 9807. Unlike traditional password authentication where the server stores a hash of the password, OPAQUE ensures the server never learns the plaintext password, even during the registration step. Authentication produces a shared session key that can seed further encrypted communication.

This is conceptually similar to what Firefox has offered for 20+ years through its account system, but built on a formally analysed protocol with stronger security proofs.

### Brave Premium — Privacy Pass (RFC 9576)

Premium subscription validation is built on the Privacy Pass protocol, which separates **who paid** from **who is using the service**. The full credential lifecycle is described in the [Premium Account Privacy](./premium-account-privacy) page, but the core algorithm is:

<Steps>
  <Step title="Blind the token">
    The browser generates a random token and blinds it using a VOPRF (see below) so the signer cannot see the original value.
  </Step>
  <Step title="Blind signing">
    The Challenge Bypass Server (CBR) signs the blinded token. It never sees the underlying token.
  </Step>
  <Step title="Unblind and verify">
    The browser removes the blinding factor, producing a signed credential, and verifies a DLEQ (Discrete Log Equality) batch proof to confirm the signature was made with the correct issuer key.
  </Step>
  <Step title="Present">
    When accessing a premium service, the browser presents the unblinded credential. The service verifies it with the CBR without learning the user's identity.
  </Step>
</Steps>

### Brave Rewards — VOPRF (RFC 9497)

The Verifiable Oblivious Pseudorandom Function (VOPRF) is the cryptographic core under both Brave Rewards and the Privacy Pass implementation. A VOPRF lets a client obtain `F_k(x)` — the value of a server-keyed PRF evaluated on input `x` — without the server learning `x`, and without the client learning the key `k`. The "verifiable" part means the server provides a proof that the output was computed correctly.

In Brave Rewards, this ensures that earning BAT rewards and redeeming them at premium services are unlinkable events, even to Brave's own infrastructure.

### Brave Leo — HPKE + Oblivious HTTP (RFC 9458)

Brave's Leo AI assistant routes requests through an **Oblivious HTTP (OHTTP)** relay to prevent the AI inference backend from observing the user's IP address.

OHTTP uses **Hybrid Public Key Encryption (HPKE)**, a modern key encapsulation framework that composes a Key Encapsulation Mechanism (KEM), a Key Derivation Function (KDF), and an Authenticated Encryption with Associated Data (AEAD) algorithm. The concrete suite used follows RFC 9458.

The OHTTP architecture ensures that:
- The **relay** knows the client's IP but not the request content.
- The **gateway/backend** knows the request content but not the client's IP.
- Neither party alone can correlate identity with content.

The chunked OHTTP variant ([draft-ietf-ohai-chunked-ohttp](https://datatracker.ietf.org/doc/draft-ietf-ohai-chunked-ohttp/)) is used to support streaming responses from the inference service.

### Brave Wallet

The Wallet implements four distinct signature schemes to cover the range of blockchain networks Brave supports:

<Tabs>
  <Tab title="ECDSA / Secp256k1">
    Used for **Ethereum, Bitcoin, Filecoin (public), and Zcash (transparent)** transactions. The Secp256k1 Koblitz curve is not required by TLS — Brave adds it explicitly. While ECDSA is present in Chromium for certificate handling, the Wallet applies it to sign arbitrary blockchain transaction payloads.

    ```
    Curve:     Secp256k1
    Algorithm: ECDSA
    RFC:       SEC 2 / ANSI X9.62
    Used for:  ETH, BTC, FIL, ZEC transparent
    ```
  </Tab>
  <Tab title="EdDSA / Ed25519">
    Used for **Solana and Cardano** transactions. Ed25519 offers fast, deterministic signatures and strong security with small key sizes. The underlying mathematics (Twisted Edwards curve over the Curve25519 prime field) is also used in Chromium's TLS stack, but Brave signs blockchain messages rather than TLS handshake data.

    ```
    Curve:     Ed25519
    Algorithm: EdDSA
    RFC:       RFC 8032
    Used for:  SOL, ADA
    ```
  </Tab>
  <Tab title="Sr25519 (Unreleased)">
    Targeted at **Polkadot (DOT)** support, not yet released. Sr25519 is Schnorr signatures applied over the Ristretto255 group, which uses Ed25519's underlying field but clears the cofactor using the Ristretto technique. This avoids the small-subgroup vulnerabilities present in raw Edwards curves and supports non-interactive threshold multisig schemes.

    ```
    Curve:     Ristretto255 (Ed25519 field)
    Algorithm: Schnorr (Sr25519)
    Used for:  DOT (incoming)
    ```
  </Tab>
  <Tab title="BLS12-381">
    Used only when a user **imports an existing Filecoin account** that uses BLS keys. BLS12-381 is a pairing-friendly curve that enables signature aggregation — multiple signatures can be combined into one, reducing on-chain data. Brave does not generate BLS keys by default; this scheme is activated on demand at import time.

    ```
    Curve:     BLS12-381
    Algorithm: BLS signature scheme
    Used for:  FIL (imported accounts only)
    ```
  </Tab>
</Tabs>

#### Wallet Key Derivation — PBKDF2 (RFC 2898)

Before any signing key is stored on disk, the user's wallet password is stretched with PBKDF2 to produce an encryption key. PBKDF2 applies a pseudorandom function (HMAC-SHA256) iteratively to make brute-force attacks computationally expensive. The derived key encrypts the wallet's HD seed phrase in local storage.

#### Zcash Orchard — RedPallas + zkSNARKs

Brave Wallet includes support for **Zcash's Orchard shielded protocol** (ZIP-0224). Orchard uses:

- **RedPallas** — a Pallas-curve variant of the RedDSA signature scheme (itself a randomised Schnorr scheme), used for spending notes and binding signatures.
- **zkSNARKs** — succinct zero-knowledge proofs that prove transaction validity (correct value, valid spend authorization) without revealing amounts or participants.

This is the most complex cryptographic subsystem in the Wallet, and initial support targets desktop platforms.

### P3A — PPOPRF + STAR Protocol

Brave's **Private, Pseudonymized Product Analytics (P3A)** system collects anonymous usage metrics while providing formal **K-anonymity** guarantees: a single user's report is indistinguishable from at least K−1 other users' reports.

The system uses two building blocks:

<Accordion title="PPOPRF — Puncturable Partially Oblivious PRF">
A PPOPRF extends a standard OPRF with two properties:
- **Partial obliviousness**: the server evaluates the PRF on a combination of a public epoch and a private user value, learning the epoch but not the private input.
- **Puncturability**: the server can "puncture" its key at specific epoch values, making it impossible to evaluate the PRF for those epochs even if the key is later compromised.

In P3A, the PPOPRF is used to generate randomised, unlinkable report identifiers that are tied to a time epoch but not to a specific user.
</Accordion>

<Accordion title="STAR — Distributed Aggregation Protocol">
STAR (Distributed Secret Sharing for Private Threshold Aggregation Reporting) uses **Shamir Secret Sharing** to ensure that a metric is only revealed to Brave's aggregation server when at least K clients have reported the same value. Each client's report is a share; the server can only reconstruct the plaintext once it holds K shares for the same input.

The implementation lives in the open-source [sta-rs](https://github.com/brave/sta-rs) library. Technical details are described in the [Brave STAR announcement](https://brave.com/privacy-updates/19-star/).
</Accordion>

The combination means individual reports are cryptographically unlinkable across epochs (PPOPRF) and the aggregation server only learns values that are genuinely popular (STAR / K-anonymity).

## Open Source Status

Every cryptographic feature in this table is implemented in open-source code. There are no proprietary cryptographic modules in Brave Core. The relevant source paths include:

| Component | Path |
|---|---|
| SKUs / Privacy Pass SDK (Rust) | `components/skus/browser/rs/lib/src/` |
| Wallet key management | `components/brave_wallet/browser/` |
| P3A metrics | `components/p3a/` |
| Shields / Farbling | `components/brave_shields/` |
| Tor integration | `components/tor/` |
