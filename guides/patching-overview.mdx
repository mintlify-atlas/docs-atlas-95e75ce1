One of the primary goals of brave-core is to make changes to Chromium in a way that keeps Chromium rebases fast and low-friction. Because Brave ships frequent updates tightly tracking upstream Chromium versions, every patching decision has long-term maintenance consequences. This guide covers the three-tier patching strategy, when to use each tier, and which override mechanisms are available at each level.

## Priority Order

Brave Core enforces a strict preference hierarchy when modifying Chromium behavior. Always work through these tiers from top to bottom — only escalate to the next tier when the current one is genuinely insufficient.

<Steps>

### Changes Only Inside brave-core

The best kind of change is one that never touches Chromium source at all. If a feature can be implemented entirely inside `src/brave` — through new classes, new services, or new UI components that Chromium code calls into via Brave-owned hooks — that is always the first choice.

This includes:
- Adding new files under `src/brave/` and wiring them into the build
- Subclassing a Chromium class and constructing the subclass instead
- Adding new Brave-specific UI surfaces or components

Changes made entirely within brave-core never create patch files and never conflict on rebase.

### chromium_src Overrides

When a change requires altering the behavior of an existing Chromium file, the `chromium_src` directory is the strongly preferred mechanism. Files placed at `src/brave/chromium_src/` are prioritized over their upstream counterparts at compile time:

- `#include "chrome/browser/profiles/profile.h"` resolves to `src/brave/chromium_src/chrome/browser/profiles/profile.h` if that file exists.
- Compiling `chrome/browser/profiles/profile.cc` compiles `src/brave/chromium_src/chrome/browser/profiles/profile.cc` instead if it is present.

This covers C++ headers and sources, `.gn`/`.gni` build files, Mojom IDL files, TypeScript/JavaScript files, and Python build scripts.

No `BUILD.gn` changes are needed for most `chromium_src` overrides.

### Direct Patches (Last Resort)

When no `chromium_src` mechanism is sufficient — for example, adding a `virtual` keyword, making a small change inside an anonymous-namespace function, or modifying a build file in a way the override system cannot express — a direct patch to files in `src/` is acceptable.

After making the changes in `src/`, generate or update the patch files:

```bash
pnpm run update_patches
```

Patches are stored in `src/brave/patches/` and applied automatically during sync. Keep patches to one line wherever possible. Never use patches for nested logic changes.

</Steps>

## Available Override Mechanisms

<CardGroup cols={2}>

<Card title="chromium_src C++ Overrides" icon="code">
  Place `.h` and `.cc` files at the same path under `chromium_src/`. Use `#define` tricks to rename symbols, wrap upstream implementations, or replace entire classes. Use Plaster rewriters (`make_virtual`, `add_friend`, `drop_final`) instead of raw `#define` for structural changes.
</Card>

<Card title="Mojom Overrides" icon="puzzle">
  Override `.mojom` files in `chromium_src` using `[BraveAdd]` to introduce new types and `[BraveExtend]` to augment existing ones. Enums, interfaces, structs, and unions are all supported.
</Card>

<Card title="GN / GNI Build Files" icon="wrench">
  Prefer adding deps through `brave_build.gni`, which is already imported into nearly every Chromium build file. Add sources via `sources += my_brave_sources` from a Brave-owned `.gni` file rather than modifying upstream lists directly.
</Card>

<Card title="TypeScript / JavaScript Overrides" icon="brackets-curly">
  Add a file to `chromium_src` at the same path as the upstream file. Import the upstream module using the `-chromium.js` suffix alias, re-export what you keep, and replace what you change. Polymer and Lit components each have dedicated Brave overriding utilities.
</Card>

<Card title="Python Script Overrides" icon="python">
  Use `brave_chromium_utils.inline_chromium_src_override()` to inject a file from `chromium_src` into an upstream Python script. Use `override_utils` helpers to replace functions, methods, or variables with failure-on-missing safety guarantees.
</Card>

<Card title="Direct .patch Files" icon="file-diff">
  Generated by `pnpm run update_patches` and applied by `pnpm run apply_patches`. Use only when chromium_src cannot express the change. Keep patches minimal and prefer `#define`-based extensibility so brave-core can build on top without re-patching.
</Card>

</CardGroup>

## Key Principles

<Accordion title="Make patches trivial and extensible">
  The project aims for direct patches to contain only trivial, one-line changes — never nested logic. When a patch adds to a GN list, reference a variable defined in Brave code (`deps += brave_browser_window_deps`) so future additions don't require touching the patch. Use `#define` macros for logic injection points so brave-core can hook in without modifying the patch file itself.
</Accordion>

<Accordion title="Never copy entire files or functions">
  Copying an entire Chromium file into `chromium_src` means silently using stale code on every subsequent rebase. If only part of a function's logic needs changing, wrap only that part and fall back to the upstream implementation (`ChromiumImpl`) for everything else.
</Accordion>

<Accordion title="Keep .gitconfig clean">
  Ensure your `~/.gitconfig` does **not** contain the following, as trailing whitespace is load-bearing inside `.patch` files:

  ```ini
  [apply]
      whitespace = fix
  ```
</Accordion>

<Accordion title="Plaster over raw patches">
  For changes that would otherwise be direct patches, the [Plaster](/guides/plaster) semantic patching engine offers regex- and AST-based rewriting that is more robust across rebases, more auditable, and less likely to conflict when surrounding code shifts.
</Accordion>

<Note>
  `.patchinfo` files are git-ignored metadata files tracking which patches have been applied. They are created by `pnpm run apply_patches`. Run that command whenever you switch to a branch where `.patch` files have been added, modified, or removed to ensure Chromium files are up to date.
</Note>
